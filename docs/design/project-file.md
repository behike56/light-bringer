# Light Bringer プロジェクトファイル設計

Light Bringer の標準プロジェクト形式を `.lbproj` とします。1つの ZIP ファイルに、同じ保存時点の SQLite データベースとグラフ JSON を収録します。利用者はファイル1つでプロジェクトを保存、複製、受け渡しできます。

本書は macOS の単一ユーザーがローカルファイルを扱う場合を対象とします。グラフのデータモデルと単体ファイルの現行仕様は、[デスクトップアプリの設計](desktop-app.md) を参照してください。

## 1. ファイル形式

利用者が `注文管理.lbproj` を作成すると、ZIP のルートに次の3ファイルを格納します。バージョン1では、この3ファイルをそれぞれ1件ずつ収録します。

| ファイル名 | 役割 | 収録内容 |
| --- | --- | --- |
| `manifest.json` | Light Bringer の形式を識別する | 形式識別子と `container_version` |
| `project.sqlite` | プロジェクトの正本 | Light Bringer SQLite スキーマ（`user_version` が `1` または `2`） |
| `graph.json` | 受け渡し用のグラフを収録する | グラフ交換形式（`format_version` が `1` または `2`） |

`manifest.json` は UTF-8 の JSON とします。

```json
{
  "format": "light-bringer-project",
  "container_version": 1
}
```

コンテナ、SQLite、グラフ JSON のバージョンを個別に管理します。コンテナのバージョン1では、SQLite とグラフ JSON の形式がともに1、またはともに2の組み合わせを扱います。新規保存と再保存には形式2を使います。 [DDDモードと形式2の設計](event-storming.md#5-データモデルと保存)

`project.sqlite` は、単体で読み込める状態のデータベースとします。トランザクションを確定し、接続を閉じた一時データベースを収録します。SQLite が使用するジャーナルや WAL の補助ファイルは一時作業領域で扱います。 [SQLite の WAL 仕様](https://sqlite.org/wal.html)

## 2. ファイル操作と移行

新規プロジェクトの保存先には `.lbproj` を使います。既存の単体ファイルから移行する場合は、変換先の `.lbproj` を新規作成します。

| 操作 | 初版の挙動 |
| --- | --- |
| 新規 | モードと保存先を選び、空の `.lbproj` を作成する |
| 開く | `.lbproj` または既存の Light Bringer `.sqlite` を開く |
| 保存 | 開いている形式で、グラフと配置を確定する |
| 別名で保存 | 編集中のグラフを新しい `.lbproj` に保存する。成功後は新しいファイルを編集対象にする |
| JSON 取込 | `.json` を検証し、利用者が指定した保存先に `.lbproj` を新規作成する |
| JSON 書出 | 開いているプロジェクトの最後に保存したグラフを `.json` 単体で書き出す |

形式1の単体 SQLite は「保存」の際に同じトランザクションで形式2へ更新します。元のファイルを残して `.lbproj` に移行するには「別名で保存」を使います。既存の ID、関係、出典、配置は移行先へ引き継ぎます。保存先に同名ファイルがある場合は、別のファイル名を求めます。

未保存の変更があるプロジェクトを閉じるか切り替える場合は、「保存」「破棄」「キャンセル」を提示します。「保存」から続行するのは保存成功後です。別のプロジェクトを開けなかった場合や保存先の選択を取り消した場合は、現在のプロジェクトを表示し続けます。「破棄」を選んだ場合の変更の破棄は、閉じるか切り替える操作が成立した時点で行います。

ウィンドウを開いたままプロジェクトを閉じる操作は、[プロジェクトを閉じる機能の設計](close-project.md) を参照してください。

## 3. 読み込みと整合性検証

1. ZIP とマニフェストを検証します。バージョン1では、表にある固定名の通常ファイルだけを受け付けます。ファイル名の重複、欠落、未対応形式はエラーとします。
2. エントリを展開する前に件数とサイズを確認し、展開中にもファイルごとと全体の実バイト数を制限します。SQLite は、アプリが作成した一時ディレクトリ内の固定パスに取り出します。ZIP 内の名前は作業先パスの組み立てに使いません。
3. SQLite を読み取り専用で開き、`PRAGMA quick_check`、`application_id`、`user_version` を確認します。JSON は `format_version` を検証します。既存のグラフ検証を両方に適用し、必須項目、ID の重複、参照先、座標の有限性を確認します。
4. SQLite と JSON の形式バージョン、プロジェクトのモード、グラフを照合します。レコードを ID で対応付け、カード種別と関係種別を含む全属性、始点と終点、座標を比較します。座標は JSON との往復で元の `f64` 値を復元できる精度を確保します。未配置ノードの表示用座標は照合後に補完します。
5. 一致したグラフを編集状態に切り替えます。エラー時は読み込みを中止し、問題のあるファイル名または項目を表示します。

破損した `.lbproj` から有効な `graph.json` を取り出せる場合は、「JSON 取込」で別のプロジェクトを作成できます。ZIP として別フォルダに展開し、復元先には新しいファイル名を選びます。

## 4. 保存と同時編集

### 保存手順

1. 詳細フォームの入力を検証し、編集中のグラフと配置を1つのスナップショットとして取得します。
2. 同じスナップショットから一時 SQLite と `graph.json` を生成します。マニフェストを加え、保存先と同じディレクトリに一時 ZIP を書き込みます。
3. ZIP の書き込みを完了し、ファイルを同期します。既存ファイルを更新する場合は、保存先のファイル識別情報と内容のハッシュを、読み込み時または直近の置換直後に記録した値と照合します。
4. 既存ファイルを更新する場合は、一時 ZIP で `.lbproj` を一括置換します。新規作成と別名保存では、保存先に同名ファイルがない場合に限り確定します。
5. 保存先ディレクトリの同期後に保存済みと表示し、次回の外部変更検出に使う基準を更新します。保存中のファイル処理はバックグラウンドで行います。

置換前に失敗した場合は、前回版と編集中の変更を保持します。置換後の同期に失敗した場合は、保存内容の永続化を確認できなかった旨を表示します。置換済みファイルの識別情報を保持し、編集中の内容から再試行できる状態にします。

### 編集セッション

`.lbproj` の編集ロックは、正規化した保存先パスを基準にします。ファイル本体の置換をまたいで、プロジェクトを閉じるまでロックを保持します。同じ保存先を指すシンボリックリンクと、ファイルシステムが同一視する名前の表記は、同じロックに解決します。初版ではハードリンクを持つ `.lbproj` は読み込み時と保存直前にエラーとして扱います。

同一 Mac・同一ユーザーの別セッションがロックを保持している場合は、編集開始を止めます。保存前の照合で外部からの変更・移動・置換を検出した場合は上書きを中止し、別名保存で編集中の内容を退避できるようにします。

## 5. 実装範囲と検証

`project` モジュールが ZIP の読み書き、整合性検証、`.lbproj` の編集ロックとファイル置換を担います。既存の `storage` は SQLite の処理を、`exchange` は JSON の処理を担います。`ui` はファイル操作を呼び出し、結果と保存状態を表示します。

| 検証対象 | 確認する結果 |
| --- | --- |
| 保存と再読込 | 空のグラフと、ノード・関係・出典・配置を含むグラフを保存できる。SQLite と JSON の内容が一致し、再読込で復元される |
| 既存ファイルの移行 | `.sqlite` の別名保存と `.json` の取り込みで、元ファイルを保ったまま `.lbproj` が作られる |
| 不正ファイル | 必須ファイルの欠落・重複、未対応バージョン、不正なエントリ名、展開上限の超過、SQLite と JSON の不一致を検出する |
| 保存中の障害 | 一時ファイル作成・ZIP 書き込み・置換の各段階で障害を起こし、前回版と編集中の変更を保持できる。後段の同期に失敗した場合は再試行できる |
| 同時編集と外部変更 | 2つ目の編集セッションを拒否し、置換後もロックを保持する。編集中のファイルの外部変更を検出した場合は上書きしない |
| 性能 | 代表グラフでコンテナサイズ、読み込み時間、保存時間を計測する |

保存ごとに ZIP 全体を書き直すため、保存時間と一時ディスク使用量はデータ量に応じて増えます。代表グラフの規模、保存時間の目標、展開サイズの上限は要確認です。

Finder からのダブルクリック起動は、配布用 `.app` の整備時に扱います。`Info.plist` に独自の書類形式と `.lbproj` 拡張子を登録し、ファイルを開く通知をアプリの読み込み処理に渡します。 [Apple の書類形式定義ガイド](https://developer.apple.com/documentation/uniformtypeidentifiers/defining-file-and-data-types-for-your-app)
