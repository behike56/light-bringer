# Light Bringer Neo4j 導入設計

**ステータス**　設計案  
**調査基準**　2026年11月21日、GitHub `main` のコミット `537e719`  
**想定読者**　Light Bringer の設計・実装・運用の担当者

Light Bringer の編集データはローカルプロジェクトに保存し、確定したグラフを Neo4j に一方向で公開します。最初の検証では、既存の JSON 書き出しを使い、日常の保存操作から切り離して経路探索を試します。GraphRAG は、定型検索で取得できる根拠を自然言語の回答に活用する段階で導入を判断します。

## 1. 現行設計と導入方針

### 確認した現行仕様

- Rust デスクトップ版はメモリ上の `Graph` を編集します。標準形式の `.lbproj` は、同じ保存時点の `project.sqlite` と `graph.json` を ZIP に収録します。読み込み時は両者の内容を照合します。 [プロジェクトファイル設計](https://github.com/behike56/light-bringer/blob/537e719/docs/design/project-file.md)
- `ProjectFile` は `.lbproj` と旧単体 SQLite の読み書きを扱います。JSON 書き出しは、編集中のグラフから独立した `ProjectFile::saved_graph()` を使います。 [ProjectFile](https://github.com/behike56/light-bringer/blob/537e719/apps/desktop/src/project.rs#L16-L80) · [JSON 書き出し](https://github.com/behike56/light-bringer/blob/537e719/apps/desktop/src/ui/files.rs#L277-L296)
- 旧 PoC は Neo4j を使っていました。当時の GraphQL スキーマは、ノードの ID とラベルを返す疎通確認用です。現行版からの移行には、現在のグラフモデルとファイル契約を適用します。 [旧 PoC のスキーマ](https://github.com/behike56/light-bringer/blob/a5e820f/shard/schema.graphql) · [デスクトップアプリの設計](https://github.com/behike56/light-bringer/blob/537e719/docs/design/desktop-app.md)

### 選択肢と判断

| 方式 | 適する用途 | トレードオフ |
| --- | --- | --- |
| ローカルファイルを正本とし、Neo4j に明示的に公開する | 定型経路検索、共有閲覧、GraphRAG の検証 | オフライン編集を保てます。検索結果の鮮度は公開頻度に依存します。**初期の推奨案です。** |
| Neo4j を編集の正本にする | 複数人が同じプロジェクトを更新する共有編集 | 更新の集約が可能です。保存に接続可用性、競合検出、中央バックアップが必要になります。 |
| ローカルと Neo4j の双方で編集し、同期する | 複数端末でオフライン編集を続ける運用 | オフラインと共有編集を両立できます。項目ごとの競合、削除、再送の扱いを決める必要があります。 |

## 2. グラフのデータモデル

現行モデルの UUID、関係の方向、モード、任意属性、配置を復元できる形で保存します。Cypher のラベルと関係タイプは固定し、利用者が入力する名前や DDD の種別はプロパティとして保持します。

| Light Bringer | Neo4j での表現案 |
| --- | --- |
| プロジェクト | `:LBProject`。新設する `project_id`、`mode`、公開済みリビジョンを保持します。 |
| ノード | `:LBNode`。`project_id`、既存の UUID、`name`、`kind`、`description`、`source_reference`、`event_storming_kind` を保持します。 |
| 有向エッジ | 始点から終点への `:LB_REL`。`project_id`、既存の UUID、表示名の `label`、`note`、`source_reference`、`event_storming_relation` を保持します。同じ端点間の複数の関係も UUID で区別します。 |
| 配置 | `:LBNode` の任意の `x`・`y`。配置済みなら有限の値を両方持ち、未配置なら両方を欠損として扱います。 |

`LBProject.project_id` に一意制約を設けます。`LBNode` と `LB_REL` には、それぞれ `(project_id, id)` の複合一意制約を設けます。必須属性の存在、両端点のプロジェクト一致、DDD の接続規則は取り込み側で検証します。関係名と関係種別を別々に保持し、型付きの関係にはフリーモードでも既存の端点規則を適用します。 [現行のグラフモデルと検証](https://github.com/behike56/light-bringer/blob/537e719/apps/desktop/src/graph.rs) · [Neo4j の一意制約](https://neo4j.com/docs/cypher-manual/current/schema/constraints/create-constraints/)

現行の交換形式にプロジェクト ID はありません。初期案では、公開先を登録するときに UUID を発行し、公開設定で管理します。ファイルを移動した場合は既存の登録先を選び、別名保存したコピーを独立して公開する場合は新しい登録先を作ります。ファイル名、パス、内容ハッシュは、それぞれ変化し得るためプロジェクトの識別子から切り離します。 [現行の交換形式](https://github.com/behike56/light-bringer/blob/537e719/apps/desktop/src/exchange.rs#L13-L31)

## 3. 永続化の境界と公開パイプライン

### コンポーネントの責務

| コンポーネント | 責務 |
| --- | --- |
| `graph`、`project`、`storage`、`exchange` | 現行のグラフ検証とローカル保存・読み込みを担当します。 |
| Neo4j への公開処理 | 検証済みの保存スナップショット、公開先の `project_id`、期待リビジョン、公開要求 ID を受け、確定したリビジョンを返します。接続、データ変換、書き込みを担当します。 |
| 検索処理 | アクセスを許可したプロジェクト、検索条件、探索上限を受け、グラフ上の経路・出典・公開リビジョンを返します。接続と Cypher を検索側に閉じ込めます。 |

初回検証は `JSON 書出 → 取り込みツール → Neo4j` の経路を使います。利用者がアプリ内から公開する段階では、`ProjectFile::saved_graph()` で取得したスナップショットを同じ公開処理に渡します。

### 公開単位と再試行

1. 公開先の現在のリビジョンを確認し、その値を公開要求の期待リビジョンとして固定します。入力を読み込み、既存の `Graph::from_records` で検証します。検証後のグラフを UUID 順に正規化し、内容ハッシュを計算します。
2. Neo4j 側で対象プロジェクトの書き込みを直列化します。同じ公開要求 ID の確定記録があれば、期待リビジョンと内容ハッシュを照合して以前の結果を返します。同じ ID に異なる入力が渡された場合は拒否します。新しい要求は、現在のリビジョンが期待値と一致する場合に進めます。
3. 一つのトランザクションでノードと関係を反映し、入力から消えた対象プロジェクトのレコードを削除します。任意属性が欠損に変わった場合は古い値を除去します。同じ UUID の関係で端点が変わった場合は、旧関係を削除して新しい端点に作り直します。
4. グラフ更新、リビジョンの繰り上げ、公開要求の確定記録を同時にコミットします。通信断で結果が不明なときは、同じ要求 ID で照会または再送します。後から届いた古い要求は、期待リビジョンの照合で止めます。 [Neo4j のロックと分離レベル](https://neo4j.com/docs/operations-manual/current/database-internals/concurrent-data-access/) · [Cypher の MERGE と制約](https://neo4j.com/docs/cypher-manual/current/clauses/merge/)

検索では、グラフを取得する前後に同じ接続先で公開リビジョンを読みます。値が変わっていた場合は、途中で更新された結果を破棄して再取得します。画面や取り込み結果では、ローカル保存と Neo4j への公開を別の状態として示します。

リビジョンの照合が防ぐのは、公開要求の確定順が入れ替わることによる上書きです。古い JSON を最新の公開版に対して新規に公開できるため、取り込み時には元ファイルと公開先を表示し、利用者が対象を確認できるようにします。

仮に全量更新が性能目標を超えた場合は、別リビジョンの領域へ分割投入し、検証完了後に公開先を切り替える方式を検討します。その場合は、一意キーにリビジョンを追加し、検索中の版を保持する期間も定義します。

## 4. Cypher 検索と GraphRAG

### 定型の経路検索

初期の評価質問は「指定したコマンドをどの集約が処理し、どのイベントを発行し、どのポリシーが反応するか」です。コマンドを起点に、関係種別 `handled_by → emits → triggers` を方向付きでたどります。入力をパラメーター化し、対象プロジェクト、許可する関係、最大経路長、返却件数を指定します。結果にはカードと関係の UUID、表示名、出典、公開リビジョンを含めます。 [EventStorming の関係種別](https://github.com/behike56/light-bringer/blob/537e719/apps/desktop/src/graph/event_storming.rs#L101-L128)

### GraphRAG の追加条件

質問からカード名・説明を検索して起点を選び、Cypher で取得した周辺の経路を根拠として LLM に渡します。質問の言い換えで起点を見つけにくいことが評価で確認できたら、ベクトル検索を候補にします。評価には、正しい起点と経路を回収できた割合、回答の主張を出典で裏付けられる割合、根拠不足時に回答を保留できるかを使います。 [Neo4j GraphRAG の検索方式](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_rag.html#retrievers)

現行の `source_reference` は任意の文字列です。初期は入力された参照情報を根拠に添えます。原文の引用が必要になった段階で、文書 ID、版、節またはチャンクを表す参照モデルを追加します。 [現行の出典フィールド](https://github.com/behike56/light-bringer/blob/537e719/apps/desktop/src/graph.rs#L19-L45)

## 5. マイグレーションと復旧

1. `.lbproj`、単体 SQLite、JSON を既存の読み込み経路で検証します。SQLite と JSON は形式 1・2 を対象とし、形式 1 は現行どおりフリーモードとして扱います。`.lbproj` は内包する SQLite と JSON の照合を経て取り込みます。
2. 対象の公開先、入力形式、ノード・関係・配置の件数、検証エラーを確認します。Neo4j 側のスキーマの版は、入出力形式の版と独立して管理します。
3. Neo4j から読み戻したレコードを `Graph::from_records` に渡し、元のグラフと比較します。ID、方向と端点、任意属性、モード、座標まで一致することを確認します。空グラフや削除を含む更新でも照合します。
4. 公開データを再構築する際は、対象のローカル保存済み版を確認して再公開します。正本を Neo4j に切り替える段階では、書き込みを止めて最終照合し、切替後の更新も含めて `.lbproj` に書き戻して開けることを復旧条件にします。 [現行のファイル互換性と照合](https://github.com/behike56/light-bringer/blob/537e719/docs/design/project-file.md) · [既存の往復テスト](https://github.com/behike56/light-bringer/blob/537e719/apps/desktop/src/project_tests.rs#L370)

## 6. 運用と受け入れ条件

| 観点 | 受け入れ条件または測定方法 |
| --- | --- |
| 可用性 | Neo4j に接続できない状態で、ローカルの保存と再読込に成功します。復旧後に保存済みの版を公開できます。 |
| 整合性と再送 | 書き込み途中で例外を発生させ、公開済みデータが前回の版を保つことを確認します。コミット直後の通信断を再現して同じ要求を再送し、リビジョンの二重更新がないことを確認します。 |
| 競合と境界 | 同じ期待リビジョンからの競合する更新は一方だけが確定します。別プロジェクトに同じノード・関係 UUID があっても、更新・削除・検索は対象プロジェクトに限定されます。 |
| 性能と鮮度 | 既存の合成データである 1 万ノード・3 万関係を起点に、初回公開、再公開、検索反映までの時間を測ります。経路検索の p95 と、関係が集中するノードでの探索負荷も測ります。 |
| 権限と機密性 | 公開用と検索用の認証情報を分けます。検索側の資格情報で書き込めないことを確認します。プロジェクトへのアクセス制御はサービスまたは DB 側で行います。外部 LLM に渡す説明・注記・出典は、送信を許可した範囲に限定します。 |
| 運用と復旧 | 公開先、公開リビジョン、件数、処理時間、失敗原因を記録します。Neo4j が検索用であれば元ファイルからの再構築時間を測ります。正本にする場合は、必要な復旧時間と許容データ損失を定め、バックアップから復元します。 |

接続には TLS を使い、資格情報はアプリのプロジェクトファイルから分離します。Rust から直接接続する場合は、Neo4j Labs の `neo4rs` を候補とし、対象版の組み合わせで TLS、トランザクション、通信断からの復帰を確認します。セルフホストとマネージドサービスの選定には、保守負荷とバックアップ・復元の要件を使います。 [既存の計測データ](https://github.com/behike56/light-bringer/blob/537e719/apps/desktop/src/project_tests.rs#L480-L536) · [neo4rs](https://github.com/neo4j-labs/neo4rs) · [Neo4j のバックアップと復元](https://neo4j.com/docs/operations-manual/current/backup-restore/)

## 7. 段階的な導入と未決事項

1. **公開と往復変換。** 既存の JSON 書き出しを使い、ローカル保存から独立した公開、再送、読み戻しを検証します。
2. **定型検索。** 実際のプロジェクトで経路、出典、検索性能を評価し、利用者が使う質問と許容する鮮度を決めます。検索価値が確認できたら、アプリからの公開・検索を検討します。
3. **GraphRAG。** 質問の言い換えや出典を伴う回答に需要がある場合に、全文検索、ベクトル検索、原文参照の効果を評価します。
4. **共有編集。** 同じグラフを複数人で更新する要件が具体化した場合、プロジェクト ID ベースで開く・再読込する・保存する境界を設けます。UI には接続先の選択と認証を追加します。期待リビジョン付きの保存で競合を検出し、競合や保存結果不明時には編集中の内容を保持します。利用者は再読込または退避を選べます。オフラインでの共有編集には、永続キャッシュと競合解決規則も必要です。

設計レビューでは、最初に答えたい質問、公開を担当する人、対象プロジェクトの規模と権限を確定します。その判断と初期計測を基に、検索応答と公開遅延の目標、Neo4j の版・運用形態、外部 LLM に送信できる情報の範囲を決めます。
